# Caching Architecture — NL-to-SQL Pipeline

The NL-to-SQL pipeline uses a three-layer caching strategy to minimize LLM calls, reduce latency, and improve determinism. Each layer serves a distinct purpose with its own storage, lifetime, and invalidation strategy.

---

## Layer Overview

| Layer | Storage | Lifetime | Latency | Source Badge (UI) |
|-------|---------|----------|---------|-------------------|
| 1. NLTK Fingerprint Match | Postgres (`golden_query_patterns.fingerprint`) | Persistent | ~0.5s | Green "Catalog" |
| 2. In-Memory Query Cache | RAM (`Map<string, string>`) | Until server restart | ~0ms | Blue "Cached" |
| 3. Golden Query Catalog | Postgres (`golden_queries` + `golden_query_patterns`) | Persistent | N/A (backing store) | — |

---

## Layer 1: NLTK Fingerprint Match (Postgres)

**Tables:** `golden_query_patterns` (fingerprint column), `golden_queries`
**Code:** `scripts/query_matcher.py` — `load_fingerprints()`, `cmd_build_fingerprints()`

### What it stores
Pre-computed lemmatized token fingerprints for every pattern in the `golden_query_patterns` table. Each pattern is processed through the NLTK pipeline (tokenize → remove stopwords → POS-tag → lemmatize) and the resulting token set is stored in a Postgres `TEXT[]` column so it doesn't need to be recomputed on every match.

### Schema
```sql
-- golden_queries
CREATE TABLE golden_queries (
  id          SERIAL PRIMARY KEY,
  sql         TEXT NOT NULL,
  description TEXT DEFAULT '',
  source      TEXT DEFAULT 'curated',
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- golden_query_patterns
CREATE TABLE golden_query_patterns (
  id              SERIAL PRIMARY KEY,
  golden_query_id INT REFERENCES golden_queries(id) ON DELETE CASCADE,
  pattern         TEXT NOT NULL,
  fingerprint     TEXT[] DEFAULT '{}',
  created_at      TIMESTAMPTZ DEFAULT now()
);
```

### Invalidation
- **No cache file to invalidate.** Fingerprints are stored alongside patterns in Postgres.
- **Auto-computed at learn time:** When `cmd_learn()` inserts a new pattern, it computes and stores the fingerprint in the same transaction.
- **Manual rebuild:** `python3 scripts/query_matcher.py build-fingerprints` recomputes all fingerprints.

## Layer 2: In-Memory Query Cache (RAM)

**Location:** `queryCache` variable in `src/lib/nl-to-sql.ts`
**Type:** `Map<string, string>` — normalised question text → SQL string

### What it caches
SQL generated by the Claude LLM for questions asked during the current server process. If the same question (after normalisation) is asked again within the same session, the cached SQL is returned without calling either the NLTK matcher or the LLM.

### Invalidation
- **Server restart:** The Map is lost when the Next.js process restarts.
- **No explicit eviction:** The cache grows unbounded within a session. For a dashboard application with limited concurrent users, this is acceptable.

### Why it exists
Even though the `learn` command persists LLM-generated queries to Postgres, there's a window between when the LLM generates SQL and when the next `match` call picks it up. The in-memory cache covers this window, ensuring zero-latency responses for repeat questions within the same session.

---

## Layer 3: Golden Query Catalog (Postgres, Persistent)

**Tables:** `golden_queries`, `golden_query_patterns`
**Code:** `scripts/query_matcher.py` — `cmd_learn()`, `load_fingerprints()`

### What it stores
The authoritative collection of question→SQL mappings. Contains two types of entries:

**Hand-curated entries** (`source = 'curated'`):
- Seeded from `references/golden-queries.json` via `scripts/seed_golden_queries.py`
- High-quality, manually verified SQL

**Auto-learned entries** (`source = 'learned'`):
- Created automatically when the LLM generates SQL that executes successfully
- Should be periodically reviewed and promoted or pruned

### How entries are added
- **Seeding:** `python3 scripts/seed_golden_queries.py` loads entries from `references/golden-queries.json` (one-time migration).
- **Auto-learning:** When the LLM generates SQL and it executes successfully, `learnGoldenQuery()` in `nl-to-sql.ts` fires a non-blocking subprocess call to `query_matcher.py learn`. The script either:
  - Appends the question as a new pattern to an existing query (if the SQL matches)
  - Creates a new golden query with `source = 'learned'`

### Invalidation / Pruning
- **No automatic expiry.** Entries persist until manually removed.
- **Pruning strategy:** Periodically review entries with `source = 'learned'` and either promote them (change source to `'curated'`, refine the SQL) or delete low-quality ones.

### Cloud-ready
Stored in Postgres, so entries persist across container restarts, are shared across horizontal scaling instances, and survive ephemeral filesystem resets.

## Resolution Flow

```
User asks a question
│
├─── Layer 1: NLTK Matcher ───────────────────────────────────
│    python3 scripts/query_matcher.py match "<question>"
│    ├─ Loads fingerprints from Postgres (golden_query_patterns)
│    ├─ Computes NLTK fingerprint for the question
│    ├─ TF-IDF cosine similarity against all patterns
│    └─ confidence >= 0.85?
│         ├─ YES → return SQL                    🟢 Catalog
│         └─ NO  → fall through
│
├─── Layer 2: In-Memory Cache ────────────────────────────────
│    queryCache.has(normaliseCacheKey(question))
│         ├─ YES → return SQL                    🔵 Cached
│         └─ NO  → fall through
│
└─── Layer 3: LLM Generation ────────────────────────────────
     claude -p "<question>" --tools "" --model sonnet
     ├─ sanitiseSQL() → safety validation
     ├─ queryCache.set(key, sql)        ← save to Layer 2
     ├─ learnGoldenQuery(question, sql) ← save to Postgres (async)
     │   └─ fingerprint computed and stored in same transaction
     └─ return SQL                               🟡 LLM Generated
```

## Key Files

| File | Role |
|------|------|
| `src/lib/nl-to-sql.ts` | Orchestrates the 3-layer pipeline, owns the in-memory cache |
| `scripts/query_matcher.py` | NLTK matcher + learn command + Postgres fingerprint management |
| `scripts/seed_golden_queries.py` | One-time migration: seeds Postgres from `golden-queries.json` |
| `references/golden-queries.json` | Original seed data (archive — active data is in Postgres) |
| `scripts/.nltk_data/` | NLTK corpora — tokenizer, stopwords, wordnet, POS tagger (gitignored) |
