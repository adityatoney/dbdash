# Caching Architecture — NL-to-SQL Pipeline

The NL-to-SQL pipeline uses a three-layer caching strategy to minimize LLM calls, reduce latency, and improve determinism. Each layer serves a distinct purpose with its own storage, lifetime, and invalidation strategy.

---

## Layer Overview

| Layer | Storage | Lifetime | Latency | Source Badge (UI) |
|-------|---------|----------|---------|-------------------|
| 1. NLTK Fingerprint Cache | Disk (`references/golden-fingerprints.json`) | Until `golden-queries.json` changes | ~0.5s | Green "Catalog" |
| 2. In-Memory Query Cache | RAM (`Map<string, string>`) | Until server restart | ~0ms | Blue "Cached" |
| 3. Golden Query Catalog | Disk (`references/golden-queries.json`) | Permanent (manual pruning) | N/A (backing store) | — |

---

## Layer 1: NLTK Fingerprint Cache (Disk)

**File:** `references/golden-fingerprints.json`
**Code:** `scripts/query_matcher.py` — `load_fingerprints()`, `_build_fingerprints()`

### What it caches
Pre-computed lemmatized token fingerprints for every pattern in `golden-queries.json`. Each pattern is processed through the NLTK pipeline (tokenize → remove stopwords → POS-tag → lemmatize) and the resulting token set is stored so it doesn't need to be recomputed on every match.

### Structure
```json
{
  "built_at": "2026-03-29T...",
  "entries": [
    {
      "index": 0,
      "pattern": "How many members attended GP events each year?",
      "fingerprint": ["attend", "event", "gp", "member", "year"],
      "sql": "SELECT ...",
      "description": "..."
    }
  ]
}
```

### Invalidation
- **Automatic (mtime check):** On every `match` call, the script compares `mtime` of `golden-queries.json` vs `golden-fingerprints.json`. If the catalog is newer, the cache rebuilds.
- **Explicit deletion:** The `learn` command deletes this file after appending a new entry to `golden-queries.json`, forcing a rebuild on the next match.
- **Manual rebuild:** `python3 scripts/query_matcher.py build-fingerprints`

### Git status
In `.gitignore` — never committed. Regenerated automatically.

## Layer 2: In-Memory Query Cache (RAM)

**Location:** `queryCache` variable in `src/lib/nl-to-sql.ts`
**Type:** `Map<string, string>` — normalised question text → SQL string

### What it caches
SQL generated by the Claude LLM for questions asked during the current server process. If the same question (after normalisation) is asked again within the same session, the cached SQL is returned without calling either the NLTK matcher or the LLM.

### Invalidation
- **Server restart:** The Map is lost when the Next.js process restarts.
- **No explicit eviction:** The cache grows unbounded within a session. For a dashboard application with limited concurrent users, this is acceptable.

### Why it exists
Even though the `learn` command persists LLM-generated queries to `golden-queries.json`, there's a window between when the LLM generates SQL and when the fingerprint cache rebuilds. The in-memory cache covers this window, ensuring zero-latency responses for repeat questions within the same session.

## Layer 3: Golden Query Catalog (Disk, Persistent)

**File:** `references/golden-queries.json`
**Code:** `scripts/query_matcher.py` — `cmd_learn()`, read by `_build_fingerprints()`

### What it stores
The authoritative collection of question→SQL mappings. Contains two types of entries:

**Hand-curated entries** (no `source` field):
```json
{
  "patterns": ["How many members attended GP events each year?", "GP attendance by year"],
  "sql": "SELECT ...",
  "description": "Count of distinct members who checked in to GP events, grouped by year"
}
```

**Auto-learned entries** (`"source": "learned"`):
```json
{
  "patterns": ["Which zones had the most gnan ceremonies?"],
  "sql": "SELECT ...",
  "description": "Auto-learned query",
  "source": "learned"
}
```

### How entries are added
- **Manual:** Developer edits the JSON file directly.
- **Auto-learning:** When the LLM generates SQL and it executes successfully, `learnGoldenQuery()` in `nl-to-sql.ts` fires a non-blocking subprocess call to `query_matcher.py learn`. The script either:
  - Appends the question to an existing entry's `patterns[]` (if the SQL matches an existing entry)
  - Creates a new entry with `"source": "learned"`

### Invalidation / Pruning
- **No automatic expiry.** Entries persist until manually removed.
- **Pruning strategy:** Periodically review entries with `"source": "learned"` and either promote them (remove the `source` field, refine the SQL) or delete low-quality ones.

### Git status
Committed to git. The file grows over time as the system learns.

## Resolution Flow

```
User asks a question
│
├─── Layer 1: NLTK Matcher ───────────────────────────────────
│    python3 scripts/query_matcher.py match "<question>"
│    ├─ Loads golden-fingerprints.json (rebuilds if stale)
│    ├─ Computes NLTK fingerprint for the question
│    ├─ TF-IDF cosine similarity against all patterns
│    └─ confidence >= 0.85?
│         ├─ YES → return SQL                    🟢 Catalog
│         └─ NO  → fall through
│
├─── Layer 2: In-Memory Cache ────────────────────────────────
│    queryCache.has(normaliseCacheKey(question))
│         ├─ YES → return SQL                    🔵 Cached
│         └─ NO  → fall through
│
└─── Layer 3: LLM Generation ────────────────────────────────
     claude -p "<question>" --tools "" --model sonnet
     ├─ sanitiseSQL() → safety validation
     ├─ queryCache.set(key, sql)        ← save to Layer 2
     ├─ learnGoldenQuery(question, sql) ← save to Layer 3 (async)
     │   └─ deletes golden-fingerprints.json (invalidates Layer 1)
     └─ return SQL                               🟡 LLM Generated
```

## Key Files

| File | Role |
|------|------|
| `src/lib/nl-to-sql.ts` | Orchestrates the 3-layer pipeline, owns the in-memory cache |
| `scripts/query_matcher.py` | NLTK matcher + learn command + fingerprint cache management |
| `references/golden-queries.json` | Persistent query catalog (committed) |
| `references/golden-fingerprints.json` | Fingerprint cache (gitignored, auto-generated) |
| `scripts/.nltk_data/` | NLTK corpora — tokenizer, stopwords, wordnet, POS tagger (gitignored) |
